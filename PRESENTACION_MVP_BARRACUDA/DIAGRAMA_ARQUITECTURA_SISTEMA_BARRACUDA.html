2. Modelo de Capas — Detalle de cada Nivel Arquitectural § Layered Model
L0
Capa 0 — Mundo Exterior (Hardware Naval) CAPA FÍSICA

Hardware externo al ecosistema de software: Gabinete de Interfaz (IC), periféricos de entrada del operador (Joystick, Teclado), sensores de navegación (GPS, Girocompás, Inclinómetro), Sistema de Gestión de Combate (CMS) y cámaras EOT. Todos se comunican mediante protocolos de red estándar (TCP/UDP) sobre la LAN naval del buque.

🔋 IC Gabinete

Server socket TCP :6001. Protocolo binario ICD propietario. 29B TX / 31-33B RX.

🕹️ Joystick + ⌨️ Teclado

UDP :4531 (unidireccional) + UDP :5501 (bidireccional con LEDs de feedback).

🛰️ Sensores NMEA

GPS ($GPGGA), Girocompás ($HEHDT), Inclinómetro (Pitch/Roll). UDP :70xx multicast.

⚔️ CMS + 📷 Cámaras

Pistas tácticas 42B/track UDP :8000. Video H.264 RTP segregado :37511-:37513.

L1
Capa 1 — Infraestructura (Drivers de Red) ACCESO A HARDWARE

Abstrae los detalles de los protocolos de transporte (net.Socket para TCP, dgram para UDP, child_process para FFmpeg). Esta capa traduce los bytes crudos del cable en eventos del bus interno de Node.js (EventEmitter). Responsabilidad exclusiva: abrir/cerrar sockets, reconectar, parsear headers de protocolo, emitir buffers al siguiente nivel.

🔗 TCPService

net.Socket persistente :6001. Watchdog 1200ms. Reconexión automática con backoff. Singleton.

📡 UDP Drivers ×5

dgram.createSocket('udp4') × 5 instancias. Cada driver bindea a un puerto específico y emite eventos al dominio.

🎬 VideoService

child_process.spawn(ffmpeg). Proceso hijo aislado del Event Loop. Puerto dinámico: 37511 + (consoleNum - 1).

L2
Capa 2 — Dominio (Lógica Naval de Negocio) REGLAS DE NEGOCIO

El corazón intelectual del sistema. Contiene la lógica de negocio naval: protocolo binario ICD (serialización/deserialización), validación de integridad XOR, máquina de estados FSM de modos de trabajo, decodificación del Joystick con deadzone, parseo NMEA y gestión de pistas tácticas CMS. Esta capa NO sabe de sockets ni de UI — opera exclusivamente con objetos de dominio.

📦 BinaryProtocolService

Núcleo del ICD. generateFrame() 29B, parseFrame() 31B, calculateChecksum() XOR. Único punto de mutación.

🔄 FSM WorkMode

Estados: RWS (0x01) ↔ EOT (0x02) ↔ CMS Pista (0x03). Transiciones con guard clauses de seguridad.

🎯 JoystickDecoder

Deadzone ±5 en ejes X/Y/Z. Conversión signed int8. Mapeo de 12 botones a acciones tácticas.

🧭 NMEA + ⚔️ CMS + 💡 Feedback

Parseo de sensores, pistas tácticas 42B y generación de feedback LED 5B confirmado por hardware.

L3
Capa 3 — Aplicación (Orquestador EDA) COORDINACIÓN

Coordina el flujo de datos entre la Capa de Dominio y la Capa de Presentación. El server.js actúa como EventEmitter Hub: recibe eventos de la capa de dominio, ejecuta el Heartbeat Loop determinístico de 100ms y distribuye los datos procesados mediante WebSocket al frontend. StationManager gestiona la exclusividad de mando entre las 3 consolas.

🎯 server.js — Event Hub

Instancia servicios, configura listeners, ejecuta heartbeat() 100ms con compensación de drift temporal.

👥 StationManager

Exclusividad de mando: solo 1 consola activa. Asignación dinámica C1/C2/C3 con validación.

📡 WebSocketServer

ws :8001 Full-Duplex JSON. Broadcast de datos IC, NAV, CMS, STATION a todos los clientes conectados.

L4
Capa 4 — Presentación (HMI Svelte) INTERFAZ OPERADOR

Interfaz humano-máquina ejecutada en el Renderer de Electron (Chromium). Recibe datos del backend vía WebSocket y los almacena en Svelte Stores reactivos. Los componentes se suscriben a los stores y re-renderizan selectivamente. El Radar PPI es SVG vectorial puro con requestAnimationFrame para mantener ≥30 FPS. Diseño "Deep Sea" de bajo brillo para operación en puesto de combate nocturno.

📡 Radar.svelte (PPI)

SVG vectorial: círculos de rango, marcas de rumbo, vectores RWS/EOT, pistas CMS. Polar→Cartesiano.

📊 GaugePanel.svelte

Indicadores numéricos de ronza (0-359°), elevación, estado IC, modo de trabajo, nivel de señal.

🎬 VideoEOT.svelte

Canvas HTML5 con stream H.264 de la cámara EOT. Segregado por estación activa.

🔍 HackingView.svelte

Vista de auditoría: tramas TX/RX en HEX real-time para depuración y validación de integridad.

4. Patrones de Diseño Arquitectural Implementados § Design Patterns
ARQUITECTURAL

🏛️ Layered Architecture

5 capas con responsabilidades estrictamente delimitadas: Hardware → Infraestructura → Dominio → Aplicación → Presentación. Cada capa solo se comunica con la adyacente.

ARQUITECTURAL

⚡ Event-Driven Architecture (EDA)

EventEmitter de Node.js como bus de datos central. Los servicios emiten eventos y los consumidores los procesan de forma asíncrona, eliminando acoplamiento directo.

CREACIONAL

1️⃣ Singleton

BinaryProtocolService, StationManager y TCPService son instancias únicas. Garantiza consistencia global del estado y previene condiciones de carrera.

COMPORTAMENTAL

🔄 Observer (Pub/Sub)

Svelte Stores (writable) implementan el patrón Observer. Los componentes UI se suscriben y reaccionan automáticamente a cambios de estado sin polling.

COMPORTAMENTAL

🔀 State Machine (FSM)

Máquina de Estados Finita para modos de trabajo: RWS ↔ EOT ↔ CMS Pista. Transiciones validadas con guard clauses de seguridad naval.

ESTRUCTURAL

🌉 Bridge

WebSocket actúa como puente entre la capa de Aplicación (Node.js) y la capa de Presentación (Svelte/Chromium), desacoplando completamente backend de frontend.

CONCURRENCIA

🧵 Process Isolation

FFmpeg ejecuta en proceso hijo separado (child_process.spawn), aislando el procesamiento CPU-intensivo de video del Event Loop de telemetría.

SEGURIDAD

🛡️ Fail-Safe Default

Ante cualquier fallo (enlace caído, XOR inválido, timeout CMS), el sistema adopta el estado más seguro: bloquea mandos y alerta al operador.

8. Registro de Decisiones Arquitecturales (ADR) § Architecture Decision Records
ID Decisión Contexto Alternativas Evaluadas Justificación de la Elección
ADR-01 Node.js como runtime backend Sistema con 5+ fuentes de datos concurrentes sobre sockets heterogéneos Python asyncio, Go goroutines, Java NIO I/O no bloqueante nativa, Buffer API para binario, mismo lenguaje que frontend (Svelte), Event Loop cooperativo sin condices de carrera
ADR-02 Svelte 4 como framework frontend HMI de misión crítica en hardware embebido con recursos limitados React, Vue 3, Angular Compilador (no runtime), zero virtual DOM overhead, bundle mínimo, reactividad granular por store sin cascadas
ADR-03 EventEmitter como bus de datos Necesidad de desacoplar servicios sin framework externo de mensajería Redis Pub/Sub, RabbitMQ, ZeroMQ Nativo de Node.js, cero latencia de red adicional, suficiente para el volumen de eventos del sistema (~100 eventos/s)
ADR-04 FFmpeg en proceso hijo Decodificación H.264 CPU-intensiva que podría saturar el Event Loop FFmpeg en el mismo proceso, WebRTC, GStreamer child_process.spawn aísla completamente el procesamiento de video sin afectar la latencia del Heartbeat TCP de 100ms
ADR-05 WebSocket para backend→frontend Distribución de datos en tiempo real al Renderer de Electron HTTP polling, Server-Sent Events, IPC Electron puro Full-Duplex bidireccional, latencia sub-1ms en localhost, formato JSON nativo, compatible con Svelte reactivo
ADR-06 SVG vectorial para Radar PPI Representación de radar con elementos dinámicos (bearing, pistas, heading) a ≥30 FPS Canvas 2D, WebGL, librería D3.js SVG permite manipulación directa del DOM por Svelte, escalabilidad sin pérdida de calidad, menor complejidad que WebGL para este caso de uso
ADR-07 CSS puro sin frameworks UI Estilo "Deep Sea" militar con control total del rendimiento Tailwind CSS, Bootstrap, Material UI Control total del peso del bundle, eliminación de CSS no utilizado, compatibilidad garantizada con Chromium embebido en Electron
ADR-08 Electron como empaquetador Aplicación de escritorio con backend Node.js + frontend web en PC naval Linux Tauri, NW.js, aplicación web + browser externo Electron incluye Node.js completo (necesario para sockets de bajo nivel), generación .deb nativa, versión de Chromium controlada, asarUnpack para FFmpeg
